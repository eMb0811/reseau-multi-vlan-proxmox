1.4 Résolution Multi-Tenant : Séparation Rigoureuse des Deux Équipes

Lors de l'audit initial de l'hyperviseur Proxmox, une ambiguïté sur la VM 311 (routeur-tp) a été identifiée. Cette VM appartenait à un second groupe de TP. Afin d'éradiquer tout risque de collision d'adresses IP ou d'interférences réciproques, la stratégie de séparation suivante a été mise en œuvre :

  • Rétablissement de l'environnement Groupe 1 : La VM 311 a été restaurée à son snapshot initial Final (IP WAN 10.153.4.173) et confinée exclusivement sur le pont virtuel vmbr1.
  • Création de notre environnement dédié Groupe 2 : Déploiement d'une nouvelle machine virtuelle VM 312 (routeur-groupe) dotée de l'adresse WAN fixe 10.153.4.174 et rattachée à son propre pont physique vmbr2.

SCRIPT CISCO IOS EXÉCUTÉ SUR COMMUTATEUR CATALYST 2950G cisco_switch_config.ios 
! ==============================================================================
! CONFIGURATION CISCO IOS DU SWITCH PHYSIQUE (COMMUTATION DE NIVEAU 2)
! Architecture : 3 VLANs segmentés + 1 Trunk 802.1Q vers l'Hyperviseur Proxmox
! ==============================================================================

! 1. Accès au mode d'exécution privilégié (Enable)
enable

! 2. Entrée dans le terminal de configuration globale
configure terminal

! ------------------------------------------------------------------------------
! 3. DÉCLARATION DES DOMAINES DE BROADCAST (VLANS)
! ------------------------------------------------------------------------------
vlan 10
 name Etudiants              ! Nommage du VLAN 10 dédié aux Étudiants
 exit

vlan 20
 name Personnel              ! Nommage du VLAN 20 dédié au Personnel administratif
 exit

vlan 30
 name Visiteurs              ! Nommage du VLAN 30 dédié aux Invités/Visiteurs
 exit

! ------------------------------------------------------------------------------
! 4. CONFIGURATION DU PORT TRUNK D'INTERCONNEXION VERS PROXMOX (vmbr2)
! ------------------------------------------------------------------------------
interface FastEthernet0/1
 description TRUNK-VERS-PROXMOX-VMBR2   ! Description explicite pour la maintenance
 switchport mode trunk                  ! Force le port en mode Trunk 802.1Q permanent
 switchport trunk allowed vlan 10,20,30 ! Liste blanche : autorise uniquement les 3 VLANs
 no shutdown                            ! Active électriquement le port physique
 exit

! ------------------------------------------------------------------------------
! 5. AFFECTATION DES PLAGES DE PORTS D'ACCÈS POUR LES POSTES CLIENTS
! ------------------------------------------------------------------------------

! --- Ports Fa0/2 à Fa0/16 : VLAN 10 (Étudiants) ---
interface range FastEthernet0/2 - 16
 description ACCES-VLAN10-ETUDIANTS
 switchport mode access                 ! Fixe le port en mode d'accès non étiqueté
 switchport access vlan 10              ! Associe le port physique au VLAN 10
 spanning-tree portfast                 ! Bypass immédiat des états d'apprentissage STP
 no shutdown
 exit

! --- Ports Fa0/17 à Fa0/32 : VLAN 20 (Personnel) ---
interface range FastEthernet0/17 - 32
 description ACCES-VLAN20-PERSONNEL
 switchport mode access
 switchport access vlan 20              ! Associe le port physique au VLAN 20
 spanning-tree portfast
 no shutdown
 exit

! --- Ports Fa0/33 à Fa0/48 : VLAN 30 (Visiteurs) ---
interface range FastEthernet0/33 - 48
 description ACCES-VLAN30-VISITEURS
 switchport mode access
 switchport access vlan 30              ! Associe le port physique au VLAN 30
 spanning-tree portfast
 no shutdown
 exit

! 6. Sortie du mode de configuration
end

! 7. Sauvegarde persistante de la configuration en mémoire non volatile
write memory                            ! Copie la running-config vers la startup-config
! Résultat retourné : [OK]

Explications Techniques des Mécanismes Clés :

  • Sécurité du Trunk (allowed vlan 10,20,30) : Limite strictement le transit aux trames appartenant à nos trois sous-réseaux. Les VLANs natifs ou non affectés sont systématiquement éliminés afin de prévenir les attaques par saut de VLAN (VLAN Hopping).
  • Spanning-Tree Portfast (Justification Indispensable) : Sans la directive portfast, le protocole Spanning-Tree 802.1D standard bloque le port pendant 30 secondes (15s en Listening, 15s en Learning) afin de détecter d'éventuelles boucles de commutation. Durant cet intervalle, la carte réseau de la station cliente tente d'émettre des requêtes DHCP DISCOVER qui sont ignorées, provoquant un échec d'attribution et l'obtention d'une adresse APIPA (169.254.X.X). L'option portfast permet au port de commuter immédiatement en état Forwarding.

3 Configuration de l'Hyperviseur Proxmox VE (10.153.4.186)

3.1 Architecture de Pontage Virtuel et Support 802.1Q

L'hyperviseur Proxmox VE exploite les fonctionnalités de pontage Ethernet du noyau Linux. Pour assurer la séparation physique et logique des flux, trois bridges distincts sont instanciés dans /etc/network/interfaces.

3.2 Fichier Intégral Commenté : /etc/network/interfaces

FICHIER DE CONFIGURATION RÉSEAU DE L'HÔTE PROXMOX VE /etc/network/interfaces 
# ==============================================================================
# CONFIGURATION RÉSEAU DE L'HYPERVISEUR PROXMOX VE (Hôte : 10.153.4.186)
# ==============================================================================

# Interface locale de bouclage
auto lo
iface lo inet loopback

# Carte physique 1 (Broadcom BCM5709) : Uplink vers le réseau du Campus
iface enp4s0f0 inet manual

# Carte physique 2 (Broadcom BCM5709) : Port Gigabit 1
iface enp3s0f0 inet manual

# Carte physique 3 (Broadcom BCM5709) : Port Gigabit 2 raccordé au switch Cisco !
iface enp3s0f1 inet manual

# ------------------------------------------------------------------------------
# PONT WAN PUBLIC (vmbr0) : Management Proxmox & Sortie Internet des VMs
# ------------------------------------------------------------------------------
auto vmbr0
iface vmbr0 inet static
    address 10.153.4.186/24          # IP fixe d'administration de l'hyperviseur
    gateway 10.153.4.254             # Passerelle amont vers l'infrastructure école
    bridge-ports enp4s0f0            # Associe l'interface physique WAN
    bridge-stp off
    bridge-fd 0

# ------------------------------------------------------------------------------
# PONT RÉSERVÉ GROUPE 1 (vmbr1) : Machine VM 311 de l'autre équipe
# ------------------------------------------------------------------------------
auto vmbr1
iface vmbr1 inet static
    address 192.168.100.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0

# ------------------------------------------------------------------------------
# PONT DÉDIÉ NOTRE GROUPE (vmbr2) : Acheminement du Trunk 802.1Q vers le Switch
# ------------------------------------------------------------------------------
auto vmbr2
iface vmbr2 inet manual
    bridge-ports enp3s0f1            # Port physique relié au câble du port Fa0/1 Cisco
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes            # Active le filtrage et le transport des tags VLAN
    bridge-vids 2-4094               # Permet le transit de tous les identifiants VLANs

Analyse Diagnostique : Correction de l'Interface Physique Active

Lors des premières vérifications, aucun bail DHCP n'était délivré aux postes clients. L'interrogation de l'état matériel via ip -s link a mis en évidence que l'interface enp3s0f0 présentait l'état NO-CARRIER (câble non branché sur cette prise). L'analyse de l'interface adjacente enp3s0f1 a révélé la présence d'une porteuse active (carrier = 1, vitesse 100 Mbps full duplex). L'esclavage immédiat de enp3s0f1 au bridge vmbr2 avec bridge vlan add dev enp3s0f1 vid 2-4094 a instantanément rétabli la communication entre la VM routeur et le commutateur physique.

4 Configuration du Routeur Linux Dédié (VM 312)

4.1 Configuration Réseau Netplan (Router-on-a-Stick)

La machine virtuelle VM 312 (Ubuntu Server 22.04 LTS) assure l'ensemble du routage inter-VLAN. L'utilitaire Netplan configure l'interface WAN ens18 et crée les 3 sous-interfaces virtuelles étiquetées 802.1Q sur l'interface LAN ens19.

CONFIGURATION NETPLAN DU ROUTEUR LINUX /etc/netplan/60-routeur-tp.yaml 
# ==============================================================================
# Configuration Netplan du Routeur Dédié Groupe (VM 312 - Ubuntu 22.04)
# ==============================================================================
network:
  version: 2
  renderer: networkd                  # Démon d'exécution systemd-networkd
  
  ethernets:
    # Interface WAN (Port virtuel VirtIO relié à vmbr0 / Réseau Campus)
    ens18:
      dhcp4: no                       # Désactivation de l'attribution dynamique
      addresses:
        - 10.153.4.174/24             # Adresse IP statique attribuée à notre groupe
      routes:
        - to: default
          via: 10.153.4.254          # Passerelle de sortie vers le réseau école
      nameservers:
        addresses:
          - 172.16.2.11              # Résolveur DNS interne du campus
          - 1.1.1.1                  # Résolveur DNS public Cloudflare

    # Interface physique LAN (Port virtuel VirtIO relié au Trunk vmbr2)
    ens19:
      dhcp4: no                       # Ne porte aucune adresse IP de niveau 3

  # ----------------------------------------------------------------------------
  # CRÉATION DES SOUS-INTERFACES VIRTUELLES ÉTIQUETÉES 802.1Q (Router-on-a-stick)
  # ----------------------------------------------------------------------------
  vlans:
    # Sous-interface pour le VLAN 10 (Étudiants)
    ens19.10:
      id: 10                          # Identifiant de tag 802.1Q = 10
      link: ens19                     # Interface parente d'acheminement physique
      addresses:
        - 192.168.10.254/24          # Passerelle par défaut des postes Étudiants

    # Sous-interface pour le VLAN 20 (Personnel)
    ens19.20:
      id: 20                          # Identifiant de tag 802.1Q = 20
      link: ens19
      addresses:
        - 192.168.20.254/24          # Passerelle par défaut du Personnel

    # Sous-interface pour le VLAN 30 (Visiteurs)
    ens19.30:
      id: 30                          # Identifiant de tag 802.1Q = 30
      link: ens19
      addresses:
        - 192.168.30.254/24          # Passerelle par défaut des Visiteurs

4.3 Pare-feu et Traduction d'Adresses (NAT Masquerade iptables)

Pour permettre aux postes des VLANs privés (192.168.10.0/24, 20.0/24, 30.0/24) de communiquer avec l'extérieur, le routeur réécrit à la volée l'adresse source des paquets par sa propre adresse WAN (10.153.4.174). Les règles sont rendues persistantes via le paquet netfilter-persistent.

RÈGLES DE PARE-FEU ET DE NAT PERSISTANTES IPTABLES /etc/iptables/rules.v4 
# ==============================================================================
# RÈGLES DE PARE-FEU ET DE TRANSLATION D'ADRESSES (Chargées au démarrage)
# ==============================================================================

# ------------------------------------------------------------------------------
# TABLE NAT : Translation d'Adresses Source (SNAT / MASQUERADE)
# ------------------------------------------------------------------------------
*nat
:PREROUTING ACCEPT [0:0]
:INPUT ACCEPT [0:0]
:OUTPUT ACCEPT [0:0]
:POSTROUTING ACCEPT [0:0]

# Règle Masquerade : Traduit l'IP source privée en IP publique ens18 lors de la sortie
-A POSTROUTING -o ens18 -j MASQUERADE

COMMIT

# ------------------------------------------------------------------------------
# TABLE FILTER : Contrôle des Flux et Routage Inter-Interfaces
# ------------------------------------------------------------------------------
*filter
:INPUT ACCEPT [0:0]
:FORWARD ACCEPT [0:0]
:OUTPUT ACCEPT [0:0]

# 1. Filtrage de Sécurité : Blocage d'une adresse MAC spécifique vers le WAN ens18
# Note : Syntaxe Linux obligatoire avec deux-points (:) et non tirets (-)
-A FORWARD -o ens18 -m mac --mac-source ac:ed:5c:11:9a:a4 -j REJECT --reject-with icmp-port-unreachable

# 2. Autorise tous les flux sortants initiés depuis n'importe quel VLAN vers le WAN
-A FORWARD -i ens19.+ -o ens18 -j ACCEPT

# 3. Suivi de connexion stateful : Autorise uniquement le trafic de retour légitime
-A FORWARD -i ens18 -o ens19.+ -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

COMMIT

4.5 Serveur Cache DNS Local (BIND9)

Le démon named (BIND9) résout les requêtes de noms de domaine des postes locaux et met en mémoire cache les résultats pour accélérer la navigation et désengorger la liaison WAN.

FICHIER D'OPTIONS DU SERVEUR CACHE DNS BIND9 /etc/bind/named.conf.options 
// ==============================================================================
// Configuration du résolveur récursif et cache BIND9
// ==============================================================================
options {
    directory "/var/cache/bind";

    // Serveurs de transfert amont (Forwarders) interrogés en cascade
    forwarders {
        172.16.2.11;    // DNS interne de l'Université
        1.1.1.1;        // Cloudflare Public DNS (Haute rapidité)
        8.8.8.8;        // Google Public DNS
    };

    // Autorise les requêtes de résolution en provenance de tous nos sous-réseaux
    allow-query { any; };

    // Écoute sur le port 53 de toutes les interfaces réseau (IPv4 et IPv6)
    listen-on { any; };
    listen-on-v6 { any; };

    // Validation cryptographique automatique de la chaîne de confiance DNSSEC
    dnssec-validation auto;
};

4.6 Sonde de Métrologie et de Surveillance Réseau (NTOPng & Redis)

La sonde NTOPng analyse les en-têtes de paquets en temps réel, quantifie la bande passante consommée par protocole et détecte les flux anormaux. Elle utilise Redis comme magasin de clés-valeurs en mémoire vive.

CONFIGURATION PRINCIPALE DE LA SONDE NTOPNG /etc/ntopng/ntopng.conf 
# ==============================================================================
# Configuration de la sonde de trafic NTOPng (Supervision Web port 3000)
# ==============================================================================

# Port du serveur Web HTTP intégré (accès : http://10.153.4.174:3000)
-w=3000

# Interfaces LAN exclusives à capturer (Trunk 802.1Q - exclusion du WAN ens18)
-i=ens19.10
-i=ens19.20
-i=ens19.30

# Déclaration exclusive des sous-réseaux locaux du LAN
-m=192.168.10.0/24,192.168.20.0/24,192.168.30.0/24

# Répertoire de stockage des données de métrologie
-d=/var/lib/ntopng

Procédure de Sécurisation et de Déblocage des Identifiants NTOPng :

  • Problème Initial : Le compte admin avec mot de passe admin était refusé en raison d'un hash MD5 persistant présent dans Redis.
  • Résolution Directe en Base : Injection directe de la clé Redis ntopng.user.admin.password avec le hash MD5 officiel de admin (21232f297a57a5a743894a0e4a801fc3) via la commande redis-cli set "ntopng.user.admin.password" "21232f297a57a5a743894a0e4a801fc3", suppression du token d'expiration de mot de passe, redémarrage du service et configuration du mot de passe permanent passer2026.

6 Journal des Incidents & Guide de Dépannage (Troubleshooting)

Ce chapitre consigne l'ensemble des anomalies rencontrées lors de la mise en place de la plateforme, les diagnostics conduits et les solutions pérennes appliquées :

Anomalie Identifiée Cause Racine Analysée Procédure Corrective Appliquée
Collision de VM (Multi-tenant) La machine VM 311 (routeur-tp) était partagée avec une autre équipe d'étudiants, risquant de créer des écrasements de configuration et de baux DHCP. Restauration immédiate de la VM 311 sur son snapshot propre Final (WAN 10.153.4.173) et rattachement à vmbr1. Déploiement de notre VM 312 dédiée (routeur-groupe, WAN 10.153.4.174) reliée à vmbr2.
Verrouillage du Port Console COM7 Erreur Python PermissionError: Access is denied lors de la tentative de connexion série vers le commutateur Cisco. Un processus client SSH/Telnet tiers (PuTTY PID 25016) était resté ouvert en arrière-plan et verrouillait l'accès exclusif au port série Windows. Arrêt propre du processus et libération du handle.
Absence de Porteuse (NO-CARRIER) sur Proxmox Le câble physique provenant du switch Fa0/1 était raccordé au second port physique de la carte Broadcom (enp3s0f1) alors que le bridge était lié à enp3s0f0. Analyse de l'état carrier des interfaces dans /sys/class/net/. Modification à chaud de la configuration réseau Proxmox pour rattacher enp3s0f1 à vmbr2 avec le flag bridge-vlan-aware.
Authentification NTOPng par défaut Rejetée Le couple admin / admin ne permettait pas de se connecter en raison d'un mot de passe hérité ou d'une clé Redis initialisée sous un hash MD5 obsolète. Écrasement direct de la clé ntopng.user.admin.password dans la base Redis avec le hash MD5 officiel de admin (21232f297a57a5a743894a0e4a801fc3), suppression du flag de premier login, redémarrage du démon et affectation du mot de passe définitif passer2026.
Filtrage ICMP par la Passerelle Campus La commande ping 8.8.8.8 échouait avec le message Packet filtered émis par la passerelle amont 10.153.4.254. Diagnostic de politique de sécurité de l'université (blocage de l'écho ICMP sortant vers l'extérieur). Preuve de bon fonctionnement du NAT établie par requêtes TCP réelles sur le protocole HTTP/HTTPS (curl -I https://www.google.com → HTTP 200 OK).
Conflit d'Adressage Local sur Station Windows La station cliente possédait une interface virtuelle VMware (VMnet1) configurée avec l'adresse 192.168.10.1/24, créant une ambiguïté dans la table de routage locale avec le VLAN 10. Diagnostic via route print et test de connectivité en liant explicitement la source à l'adresse dynamique obtenue sur l'interface physique (ping -S 192.168.10.101).
